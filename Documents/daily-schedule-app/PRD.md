# Product Requirements Document: Scram（滚蛋计划）

## 1. 产品概述

### 1.1 产品名称
| 中文名 | 英文名 | 含义 |
|--------|--------|------|
| **滚蛋计划** | **Scram** | "Scram" = 滚蛋，简短有力。"计划"强调项目管控定位。未完成的任务越滚越多，最终被 App 骂"滚蛋" |

### 1.2 Slogan
> **滚蛋计划，不是它滚蛋，就是你滚蛋。**

### 1.2.1 一句话定位
> 一个会骂你的 AI PMO —— 把项目拆解为每日可执行的计划，未完成自动延期，累积太多直接开骂，骂完你还得干。

### 1.3 目标用户画像
| 维度 | 描述 |
|------|------|
| **核心用户** | AI 浪潮下的一人公司创始人到小规模工作室（3-5 人），如独立开发者、自由设计师、小团队负责人 |
| **心理特征** | 执行力驱动型，对正经项目管理工具无感，但对"被吐槽"有微妙的好胜心 |
| **痛点** | 同时跑多个项目，任务排了很多但经常不了了之，缺乏"未完成必须处理"的闭环 |
| **使用场景** | 每天早上查看今日安排（跨多个项目），按时打卡，被延期任务吐槽，每周项目进度结算 |
| **使用频次** | 每天 3-8 次（打开查看 + 打卡 + 完成任务） |

### 1.4 核心价值主张
1. **AI PMO 式拆解** —— 输入项目目标，AI 自动拆解为里程碑和每日可执行的子任务，像有个毒舌项目经理帮你规划
2. **计划不消失** —— 未完成 ≠ 被遗忘，自动滚入次日，越滚越多
3. **被骂的驱动力** —— 任务延期会被吐槽，周末会被清算，用"不服气"驱动执行
4. **项目驱动日程** —— 以项目为主线，每个日程块归属于一个项目，进度一目了然

### 1.5 产品调性
**有趣 + 吐槽 + 轻微冒犯但不让人反感**

- 像一个毒舌但关心你的项目经理，不像正经同事有距离感，而是有朋友的感觉
- 吐槽文案有层次感：轻度调侃 → 中度吐槽 → 重度开骂
- 完成时夸你不遗余力，延期时骂你毫不留情
- 用户可以设置"骂人烈度"（正常吐槽 / 火力全开），吐槽不可关闭

## 2. 用户路径

### 2.1 完整用户路径

```
创建项目 ──→ 创建子任务（两种路径） ──→ 每日打卡流程 ──→ 周日结算
   │                    │                      │               │
   │                    │                      │               │
   │                    │                      ├─ 打开完成      │
   │                    │                      ├─ 放弃/跳过      │
   │                    │                      └─ 延期/调时间    │
   │                    │                                      │
   │                    ├─ 路径A：批量创建（一次性规划4周）      │
   │                    │   ├─ Markdown 文档上传解析             │
   │                    │   └─ AI 自动拆解里程碑+子任务          │
   │                    │                                      │
   │                    └─ 路径B：逐步添加                      │
   │                        ├─ 手动逐个创建                     │
   │                        └─ 随时 AI 辅助补充                  │
   │                                                           │
   └─ 项目名称、描述、目标日期、优先级                          │
                                                              │
   每周日 21:00 生成周报                                       │
   ├─ 本周完成率 + 评级                                        │
   ├─ 各项目进度对比                                           │
   ├─ 周评语（吐槽风格）                                       │
   └─ 下周目标自动调整                                         │
```

### 2.2 子任务创建两种路径

#### 路径 A：批量创建（一次性规划）
适用场景：项目刚启动，用户已经规划好未来几周每天要做什么

**方式 1：Markdown 文档上传解析**
- 用户按指定格式编写计划文档（如 `plan.md`），上传到 App
- App 自动解析文档中的里程碑 → 子任务 → 时间段 → 重复规则
- 解析结果预览，用户确认后批量创建
- 格式示例：
  ```markdown
  # 日历APP 项目计划
  
  ## 里程碑1：产品设计（第1周）
  - 周一 10:00-12:00 产品方案设计
  - 周二 14:00-16:00 产品方案评审
  - 周三 10:00-12:00 UI设计
  - 周四 14:00-16:00 交互原型
  
  ## 里程碑2：前端开发（第2-3周）
  - 周一~周五 10:00-12:00 首页开发（循环）
  - 周一~周五 14:00-16:00 打卡功能开发（循环）
  ```

**方式 2：AI 自动拆解**
- 用户输入项目描述（如"做一个iOS日历App，支持项目管理和吐槽功能"）
- AI 自动分析项目，拆解为里程碑和子任务
- 展示拆解结果（里程碑时间线 + 子任务列表），用户可调整确认后创建
- AI 考虑因素：项目类型、复杂度、用户历史执行效率

#### 路径 B：逐步添加
适用场景：项目进行中，根据实际进展动态调整计划

- 在项目详情页点击"+"手动添加子任务
- 随时使用 AI 辅助：输入"这周还需要完成什么"，AI 建议子任务
- 适合敏捷迭代式项目管理

## 3. 数据模型

### 3.1 四层结构

```
用户
├── 项目 A（Project）
│   ├── 里程碑（Milestone）→ AI拆解/手动创建
│   │   ├── 子任务 1（Subtask）→ 每日自动生成任务实例（TaskInstance）
│   │   ├── 子任务 2（Subtask）
│   │   └── ...
│   ├── 里程碑
│   │   └── ...
│   └── ...
├── 项目 B（Project）
│   └── ...
└── ...
```

### 3.2 核心概念

| 概念 | 定义 | 示例 |
|------|------|------|
| **项目（Project）** | 一个正在进行的工作主题，包含里程碑、循环子任务、非循环子任务 | "日历 APP"、"AI 写作工具" |
| **里程碑（Milestone）** | 项目的阶段性目标，可手动创建或 AI 自动拆解 | "产品设计"、"前端开发"、"测试上线" |
| **非循环子任务（Subtask）** | 归属里程碑的具体工作单元，有明确的起止和阶段推进 | "周一 10:00-12:00 产品设计方案50%" |
| **循环子任务（Circular Subtask）** | 不归属里程碑的贯穿项目的长线日程，如每日站会、每日代码review | "周一~周五 09:30-09:45 项目日会" |
| **任务实例（TaskInstance）** | 子任务在特定日期的具体执行单元，用户实际操作的单位 | "2026-04-28 09:30-09:45 项目日会" |

**子任务 vs 任务实例 举例**：

```
子任务 = 模板（定义"做什么"）
任务实例 = 某一天的具体执行单元（实际"做没做"）

例1：非循环子任务
  子任务："周一 10:00-12:00 产品设计方案50%"（归属里程碑1）
  → 4月28日生成实例 A：2026-04-28 10:00-12:00 [status: pending]
  → 用户延期到周二 → rollover_count=1，触发吐槽
  → 4月29日生成新实例 B：2026-04-29 10:00-12:00 [status: pending]
  → A 保持 overdue，B 是新的可执行实例

例2：循环子任务
  子任务："周一~周五 09:30-09:45 项目日会"（不归属任何里程碑）
  → 一次性生成本周 5 个实例（周一~周五各一个），用户今天就能看到
  → 周一实例只有两个按钮：[打卡] [放弃]
  → 用户点"放弃" → skipped，计入周报，触发吐槽
  → 周二实例不受影响，正常存在
```

### 3.3 实体关系

```
Project (1) ────< Milestone (1) ────< Subtask (1) ────< TaskInstance (many)
     │
     └──────────< Circular Subtask (1) ────< TaskInstance (many)
```

- 一个项目可以有多个里程碑
- 一个里程碑下有多个非循环子任务
- 一个项目下可以有多个循环子任务（不归属任何里程碑，贯穿整个项目周期）
- 一个子任务按重复规则生成对应日期的任务实例
- 任务实例是用户实际操作的单位（打卡、完成、放弃、延期）

### 3.4 循环子任务 vs 非循环子任务

**循环子任务**：
- 定义：类似"项目日会"的贯穿项目的长线日程，每个工作日/每天重复出现
- 不归属任何里程碑，直接挂在项目下
- 实例一次性生成本周/未来可见周期内的所有实例（用户今天就能看到明天的任务）
- 只有两个操作：**[打卡完成]** 和 **[放弃]**
- 放弃 = skipped，**计入周报结算**，**触发吐槽**
- 不存在"延期"概念，因为明天的实例已经存在，不需要"滚"到明天

**非循环子任务**：
- 定义：归属里程碑的具体工作单元，有阶段推进性（如周一完成50%、周二完成100%）
- 归属某个里程碑
- 实例在对应日期生成
- 有三个操作：**[打卡完成]**、**[放弃]**、**[延期]**
- 放弃 = skipped，**计入周报结算**，**触发吐槽**
- 延期 → rollover_count + 1，**触发吐槽**

### 3.5 自动延期规则（00:00 触发）

**循环子任务**：
- 昨日未完成的循环任务实例 → 自动标记为 skipped（放弃）
- 触发吐槽，计入周报
- 今日新实例已在当天存在（循环任务提前生成），不需要"生成新实例"

**非循环子任务**：
- 昨日未完成的非循环任务实例 → 自动生成今日新实例（rollover_count + 1）
- 触发吐槽
- 原实例保持 overdue 状态

## 4. 功能详细需求

### 4.1 F1 项目管理

**用户故事**
> 作为一人公司创始人，我希望同时管理多个项目的进度，每个项目有独立的完成率和进度追踪。

**功能描述**
- 创建项目：名称、描述、目标完成日期、优先级
- 编辑/删除项目：修改后不影响已生成的子任务实例
- 开启/停用项目：停用后该项目下的子任务不再生成新实例
- 项目列表入口：底部 Tab "设置" > "我的项目"

**交互规则**
- 项目列表页：卡片式展示所有活跃项目，显示项目进度条
- 创建页：表单填写，简洁
- 删除：左滑删除，弹出确认弹窗"删除项目不会影响已生成的历史任务"
- 每个项目有独立的颜色标识（用于首页卡片和项目维度统计）

**边界条件**
- 同一时间最多 10 个活跃项目（超限提示用户）
- 删除项目后，已生成的子任务实例保留

---

### 4.2 F2 子任务管理

**用户故事**
> 作为用户，我希望为每个项目设置好每天的日程安排（如周一 10-12 点产品设计），之后每天自动生成，不需要重复创建。

**功能描述**
- 创建子任务：名称、开始时间、结束时间、重复规则（每天/工作日/自定义周几/一次性）、优先级、归属项目
- 编辑/删除子任务：修改后影响后续生成的实例，不影响已生成的历史实例
- 开启/停子任务：停用后不再生成新的任务实例
- 子任务列表：归属于某个项目下，按时间顺序展示

**交互规则**
- 入口：进入项目详情 > "子任务"列表
- 创建页：表单填写，时间选择器用 iOS 原生风格
- 删除：左滑删除，弹出确认弹窗"删除子任务不会影响已生成的历史任务"
- 循环子任务在卡片上标记"循环"标识

**边界条件**
- 开始时间不能晚于结束时间
- 同一时间段最多重叠 2 个子任务（超限提示用户）
- 删除子任务后，已生成的当日任务实例保留
- 修改子任务时间后，已生成的实例不变，从次日起生效
- **循环子任务不显示"延期"按钮**，只有"放弃"和"补卡"（因为明天会自动生成新的）

---

### 4.3 F2-2 里程碑管理

**用户故事**
> 作为用户，我希望把项目拆分为几个阶段性目标（里程碑），每个里程碑下有具体的子任务，这样项目进度更清晰。

**功能描述**
- 创建里程碑：名称、目标日期、描述
- 编辑/删除里程碑：删除时将该里程碑下的子任务移到"未分类"
- 里程碑在项目详情页展示为分组标题
- 里程碑进度：该里程碑下子任务的完成率

**交互规则**
- 入口：项目详情页 > "里程碑"列表
- 创建页：表单填写（名称 + 目标日期）
- 支持拖拽排序里程碑
- 支持拖拽子任务在不同里程碑间移动

---

### 4.4 F4 AI 子任务拆解（AI Native）

**用户故事**
> 作为一人公司创始人，我有一个项目想法但不知道怎么拆解为每日可执行的计划。我希望输入项目描述后，AI 帮我自动拆解为里程碑和子任务。

**功能描述**
- **入口**：创建项目后，弹出"让 AI 帮你规划"引导卡片
- **输入**：用户输入项目描述（如"做一个iOS日历App，支持项目管理和吐槽功能，预计4周完成"）
- **AI 输出**：
  - 里程碑列表（含名称、目标日期）
  - 每个里程碑下的子任务列表（含名称、时间段、一次性或按天指定）
  - 建议的时间分配依据（基于用户历史完成率）
- **确认与调整**：用户可编辑/删除/新增子任务，确认后批量创建
- **AI 考虑因素**：
  - 项目类型和复杂度
  - 用户历史执行效率（从已有项目数据中学习）
  - 每日可承载的任务量（避免排得太满）
  - 工作日 vs 周末的节奏差异

**AI 拆解规则**
- AI 拆解**不生成循环子任务**，所有子任务均为归属里程碑的普通子任务（type=normal）
- 对于需要多天连续完成的工作（如"首页开发"），AI 按天拆分为带进度的独立子任务，例如：
  - 周一 10:00-12:00 首页开发 20%
  - 周二 10:00-12:00 首页开发 40%
  - 周三 10:00-12:00 首页开发 60%
  - ...

**交互流程**
```
创建项目 ──→ 输入项目描述
              ↓
        AI 分析中（加载动画 + 吐槽"别急，我在帮你规划"）
              ↓
        展示拆解结果：
        ┌────────────────────┐
        │ 📍 里程碑1：产品设计 │ 第1周 │
        │  周一 10:00 需求分析│
        │  周二 10:00 交互设计│
        │  周三 10:00 视觉设计│
        │                    │
        │ 📍 里程碑2：前端开发 │ 第2-3周│
        │  周一 10:00 首页开发20%│
        │  周二 10:00 首页开发40%│
        │  周三 10:00 首页开发60%│
        │                    │
        │ 📍 里程碑3：测试上线 │ 第4周  │
        │  周一 10:00 功能测试│
        │  周二 10:00 Bug修复│
        │  周三 10:00 提交审核│
        └────────────────────┘
              ↓
        [确认创建] [调整后再说]
              ↓
        批量创建子任务，进入每日打卡流程
```

**技术实现**
- MVP 阶段：调用 Claude API 进行拆解
- 系统 prompt 中注入：项目描述、用户可用时间段、历史完成率、**不生成循环子任务的规则**
- 返回结构化 JSON（里程碑 + 子任务列表）
- 需要网络，离线时该功能不可用（但手动创建仍可用）

**边界条件**
- 网络不可用 → 提示"AI 暂时离线，你可以手动创建子任务"
- AI 返回结果不合理 → 用户可手动调整后确认
- AI 拆解结果超过用户每日承载量 → 提示"看起来排得太满了，要调整吗？"

### 4.5 F5 Markdown 文档导入

**功能描述**
- **入口**：项目详情页 > "导入计划" > 选择 md 文件
- **格式要求**：

  ```markdown
  # 项目名称

```

- iOS 文件选择器（本地文件）
- 粘贴文本（用户从 Notion/其他工具复制）

### 4.6 F3 今日日程视图（首页）

**用户故事**
> 作为用户，我希望一打开 App 就能按时间线看到今天所有任务的状态，跨多个项目的任务混排在一起，延期的任务一眼就能看出来。

**功能描述**
- 顶部：日期 + 星期 + 连续打卡天数（火焰图标）+ **今日被骂次数**（💢 图标）
- **每日吐槽卡片**：日期下方、任务列表上方，每次打开 App 或下滑刷新后生成一条新的吐槽（基于今日任务状态和用户行为）
- 主体：按时间从早到晚排序的任务卡片列表
- 每张卡片展示：状态标识、任务设定时间、任务名称、归属项目（颜色标签）、操作按钮
- 点击卡片：进入任务详情（备注、历史、延期记录、吐槽历史）
- 底部：本周完成率进度条 + 距离周日结算的天数

**排序规则**
- 第一排序键：任务开始时间（从早到晚）
- 第二排序键：优先级（高 > 中 > 低）
- 第三排序键：创建时间（先创建的排前面）

**任务卡片状态（非循环子任务）**

| 状态 | 标识 | 卡片操作按钮 | 卡片样式 | 额外展示内容 |
|------|------|------------|---------|------------|
| pending（待开始） | ⏰ 空心圆 | [放弃] [延期] | 灰色 | 距离开始倒计时（分钟维度，>60分钟展示"X小时X分钟"） |
| in_progress（进行中） | 🔵 旋转圆点 | [打卡] [放弃] [延期] | 蓝色高亮 | 超过预定结束时间时，显示吐槽"超时了哦，你完成了么" |
| completed（已完成） | ✅ 绿色对勾 | 无（点击查看备注） | 绿色半透明 | — |
| overdue（已过期/延期） | ⚠️ 红色感叹号 | [补卡] [延期] | 红色渐变背景+纹理 | 延期次数（×N）+ 简短吐槽文案 |

**任务卡片状态（循环子任务）**

| 状态 | 标识 | 卡片操作按钮 | 卡片样式 | 额外展示内容 |
|------|------|------------|---------|------------|
| pending（待开始） | ⏰ 空心圆 | [放弃] | 灰色 | 距离开始倒计时 |
| in_progress（进行中） | 🔵 旋转圆点 | [打卡] [放弃] | 蓝色高亮 | 超过预定结束时间时，显示吐槽"超时了哦，你完成了么" |
| completed（已完成） | ✅ 绿色对勾 | 无（点击查看备注） | 绿色半透明 | — |
| skipped（已放弃） | ❌ 灰色叉号 | 无 | 灰色半透明 | — |

- 循环子任务**不显示"延期"按钮**，只有"打卡"和"放弃"
- 循环子任务不存在 overdue 状态，因为明天/后天的实例已经提前生成

**延期/放弃任务卡片差异化设计**
- 延期任务不单独分组，按时间线混排在列表中
- 通过卡片样式（红色渐变背景+纹理）+ 延期次数标注（如 "×3"）+ 吐槽文案来区分
- 吐槽文案随 rollover_count 分级，与吐槽系统联动
- 点击吐槽文案可展开完整吐槽
- 放弃任务（skipped）以灰色样式展示，标注"已放弃"

**交互规则**
- 点击任务卡片主体（非操作按钮区域）：进入任务详情
- 下滑刷新：重新加载当日数据，同时刷新每日吐槽

**每日吐槽卡片**
- 位置：日期下方、任务列表上方
- 触发时机：每次打开 App 或下滑刷新后生成
- 吐槽内容基于：今日任务总数、已完成数、延期任务数、用户当前行为（如刚完成一个任务、刚放弃一个任务等）
- 风格随完成度变化：
  - 全未开始 → 毒舌催促
  - 部分完成 → 调侃式
  - 全部完成 → 夸奖式（替代原有庆祝）
- 文案 72 小时内不重复
- 点击可复制，黄色渐变背景 + 🤖 emoji

**边界条件**
- 跨零点任务（如 23:00-01:00）：归属到开始日期的那一天
- 当天无任务：显示空状态插画 + "连任务都没有，今天打算躺平？"
- 当天所有任务完成：吐槽卡片变为夸夸文案 "今天全清，你是时间的统治者"

### 4.4 F4 打卡系统

**用户故事**
> 作为用户，我希望到了任务时间它自动开始，我只需要一键标记完成，或者选择放弃。

**功能描述**
- **自动开始**：任务时间到达 → 状态自动从 pending 变为 in_progress，不需要手动操作
- **打卡（完成）**：点击 [打卡] → 弹出备注输入框（可选）→ 状态变为 completed
- **放弃**：点击 [放弃] → 标记为 skipped，**触发吐槽**（待开始、进行中、延期任务均可放弃）
- **延期（仅非循环子任务）**：点击 [延期] → 弹出时间选择弹窗（默认次日同一时间，用户可自行调整）：
  - **可控调整**：今日任务调到今日其他时段，或未来任务调到任意日期 → 仅修改实例时间段，不增加 rollover_count，不触发吐槽
  - **延期**：今日任务推到明天及以后 → 生成新实例，rollover_count + 1，**触发吐槽**
- **补卡**：对 overdue 任务手动补卡 → 状态变为 completed，标记 `is_makeup = true`

**循环子任务特殊操作**
- 循环子任务只有两个按钮：**[打卡]** 和 **[放弃]**
- 不显示"延期"按钮
- 放弃 = skipped，触发吐槽，计入周报

**边界条件**
- 任务时间到达但仍在进行中（未到结束时间），用户打开 App 可看到实时状态
- 任务进行中跨入结束时间 → 自动标记 overdue（仅非循环）/ skipped（仅循环），触发吐槽
- 一天内对同一任务只能打卡一次（防止刷数据）

**补卡机制**
- 补卡只针对非循环子任务的 overdue 实例
- 补卡后状态变为 completed，标记 `is_makeup = true`
- 补卡记录在日历视图中标记为特殊颜色（如浅绿），区别于正常完成
- 补卡计入连续打卡天数
- 补卡时触发补卡专属吐槽："现在补卡跟事后道歉有什么区别？"

### 4.5 F5 自动延期引擎（核心机制）

**用户故事**
> 作为用户，我希望昨天没完成的任务能自动出现在今天的安排里，而不是消失。循环任务自动放弃，非循环任务自动延期到次日。

**功能描述**

#### 自动处理规则
1. **触发时机**：每日 00:00 系统触发（本地后台任务）或 App 启动时补偿执行
2. **扫描范围**：前一日 status = pending / in_progress / overdue 的所有任务实例（未操作的任务）
3. **自动处理**：
   - **循环子任务**：自动标记原实例为 skipped（放弃），**触发吐槽**，计入周报。今日新实例已在当天存在（循环任务提前生成一周的实例），无需生成新实例
   - **非循环子任务 + auto_rollover = true**：生成今日新实例，`rollover_count = 原实例.rollover_count + 1`，标记 `is_rollover = true`，**触发吐槽**
   - **非循环子任务 + auto_rollover = false**：不创建新实例，标记原实例为 `expired`
4. **延期上限**：同一非循环任务最多自动延期 7 次，达到上限后：
   - 停止自动延期
   - 标记 `expired`
   - 触发最高级别吐槽
5. **用户手动干预**：
   - **放弃**：用户对某个任务点击 [放弃] → 标记 skipped，**触发吐槽**，计入周报（待开始、进行中、延期任务均可放弃）
   - **可控调整**：用户点击 [延期] 调整到今日其他时段，或调整未来任务的时间 → 仅修改时间段，不增加 rollover_count，不触发吐槽
   - **手动延期**：用户点击 [延期] 推到明天及以后 → 生成新实例，rollover_count + 1，触发吐槽。时间选择器默认次日同一时间，用户可自行调整
   - **循环子任务不显示"延期"按钮**，只有"放弃"

#### 吐槽分级系统（核心差异化）

吐槽按延期次数分级，最低级别也是阴阳怪气，没有"温柔提醒"。每次随机从文案库中抽取：

| 级别 | 触发条件 | 语气 | 示例文案 |
|------|----------|------|----------|
| **L1 阴阳怪气** | rollover_count = 1-2 | 阴阳但不失幽默 | "「AI学习」又延期了？没事，计划不就是用来打破的""这个任务跟你八字不合，建议分手""说好的10点开始呢，现在都第二天了" |
| **L2 直接开喷** | rollover_count = 3-5 | 毒舌不留情面 | "「AI学习」延期3次了，你是不是根本没打算做？""你不是不会，你就是懒""这个任务已经在你桌上躺了3天了，它长蘑菇了吗" |
| **L3 终极清算** | rollover_count = 6-7 | 火力全开 | "「AI学习」延期7次，建议你直接把任务删了，别折磨自己了""你的人生有几个7天可以浪费在这个任务上""这个任务比你在这个项目上待的时间还长" |

**文案生成策略（MVP 方案）**：

吐槽文案采用 **模板引擎 + 任务上下文** 的方式生成，无需接入 AI 即可做到"结合实际任务"：

```
吐槽 = 模板(任务名称, 延期次数, 时间段, 历史完成率, 任务类型标签, 项目)
```

**模板示例**（每种级别预置 15-25 条模板）：

```
模板: "「{任务名称}」延期{N}次了，{时间段}的任务硬生生拖成了连续剧"
→ 实际: "「AI学习」延期3次了，10-12点的任务硬生生拖成了连续剧"

模板: "「日历APP」的{任务名称}都延了{N}次了，项目进度被你自己拖慢了"
→ 实际: "「日历APP」的「产品设计」都延了4次了，项目进度被你自己拖慢了"

模板: "「{任务名称}」{历史完成率}%的完成率，说实话这个任务对你来说是不是超纲了"
→ 实际: "「前端重构」25%的完成率，说实话这个任务对你来说是不是超纲了"
```

**任务类型标签**（从子任务名称自动推断，MVP 阶段预定义关键词映射）：
| 关键词 | 标签 |
|--------|------|
| 产品 / 设计 / 评审 / 规划 | 产品设计 |
| 编码 / 写代码 / coding / 开发 | 写代码 |
| 测试 / 修复 / bug | 测试修复 |
| 文档 / 报告 / 写 | 文书 |
| 会议 / 沟通 / 汇报 | 社交 |
| 学习 / 课程 / 读书 | 学习 |
| 其他 | 不知道什么鬼 |

**MVP 版本不接入 AI 的原因分析**：
- MVP 核心验证的是"吐槽督促"这一机制是否有效，而非吐槽文案的质量上限
- 模板引擎方案可以在不增加成本的前提下，做到"结合实际任务"的个性化吐槽
- 接入 AI（如调用 Claude API 生成文案）会增加：网络依赖、API 成本、响应延迟、离线不可用
- **AI 文案生成推迟到 V3**，届时作为"AI 周报助手"的一部分接入

- 推送通知中也使用对应级别的吐槽文案
- 吐槽气泡在卡片上以小图标展示（💬），点击展开

**边界条件**
- 当日任务全完成 → 不触发延期，推送夸夸通知
- 延期任务又被跳过 → 连续打卡天数中断
- 用户手动删除子任务 → 已延期的实例仍保留，但不再延期

### 4.6 F6 吐槽系统（核心差异化功能）

**用户故事**
> 作为用户，我希望这个 App 像个毒舌 PMO 一样督促我推进项目，而不是一个冷冰冰的项目管理工具。被骂的时候觉得好笑，笑完还是想去完成任务。

**功能描述**

#### 吐槽触发场景

| 场景 | 吐槽级别 | 展示方式 |
|------|----------|----------|
| 任务延期（自动） | 按 rollover_count 分级 | 卡片上的吐槽气泡 + 推送通知 |
| 手动点"延期" | 在当前级别基础上 +1 | 弹窗吐槽 → 确认延期 |
| 任务超时未完成 | L1-L2 | 推送通知 |
| 补卡完成 | L1 | 补卡专属吐槽气泡 |
| 连续跳过任务 | L2-L3 | 首页顶部横幅吐槽 |
| 周日结算（周报） | 按周完成率分级 | 完整的周报页面 + 推送 |

#### 骂人烈度设置

用户可在设置中选择：
- **正常模式**（默认）：L1-L3 正常分级，阴阳→毒舌→清算，有层次感
- **火力全开**：起始级别从 L2 开始，直接开喷，建议抗压能力强的人使用
- **吐槽不可关闭**，这是产品核心机制

#### 吐槽文案管理
- 每个级别预置 10-20 条文案
- 同一文案 3 天内不重复出现
- V2 支持用户上传自定义吐槽文案

#### 夸夸系统
完成任务同样有反馈文案，分为：
| 场景 | 示例文案 |
|------|----------|
| 按时完成 | "不错嘛，今天居然准时完成了""效率在线，继续保持" |
| 提前完成 | "提前完成？你是不是偷偷开挂了""今日 MVP" |
| 完成延期任务 | "终于把这个祖宗解决了""它滚蛋了，你赢了" |
| 当日全部完成 | "今日全清！你就是时间的统治者""完美收官，明天的你也会感谢今天的自己" |
| 连续打卡 7 天 | "连续 7 天，你已经不是从前那个你了""周冠军，实至名归" |

### 4.7 F7 推送通知

**功能描述**

| 通知类型 | 触发时机 | 默认设置 | 文案模板 |
|----------|----------|----------|----------|
| 任务提醒 | 任务开始前 5 分钟 | 开启 | "⏰ {任务名称} 要开始了，别装没看见" |
| 超时吐槽 | 任务结束时间到达，状态仍为 pending | 开启 | "⚠️ {任务名称} 已经超时了，你人呢？" |
| 延期通知 | 每日 08:00（用户可调整） | 开启 | "📌 今天有{N}个任务在等你，其中{M}个是昨天遗留的，加油哦" |
| 完成庆祝 | 当日所有任务完成时 | 开启 | "🎉 今天全部搞定！连续{N}天，你有点东西" |
| 周结算 | 每周日 21:00 | 开启 | "📊 本周结算报告来了，来看看你干得怎么样" |
| 打卡中断 | 任务进行中超过 30 分钟未完成 | 关闭（默认） | "💪 {任务名称} 都{N}分钟了，别摸鱼了" |

**静默时段**
- 默认 22:00 - 08:00 为静默时段（不发送通知）
- 用户可自定义静默时段
- 延期通知和周结算通知可豁免静默时段

**技术实现**
- 使用 Expo Notifications 本地通知 + 远程通知
- 每日任务提醒在创建任务实例时注册本地通知
- 需要获取用户推送权限授权

**边界条件**
- 用户关闭推送权限 → App 内显示引导弹窗："连通知都关了，你是打算假装我不存在？"
- App 在前台运行时 → 显示内联提醒（不触发系统通知）

## 8. 风险和依赖

### 8.1 技术风险
| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| iOS 后台任务限制 | 自动延期可能无法在 App 被杀死时触发 | 方案 A：使用 Background App Refresh；方案 B：App 每次启动时检查并补执行 |
| 本地通知数量限制 | iOS 最多 64 个 pending local notifications | 仅注册当日和次日的通知，动态注册/取消 |
| Expo 推送在 iOS 的限制 | 本地通知在 App 被杀死时可能不触发 | 测试验证，必要时用原生模块补充 |

### 8.2 iOS 推送通知限制
- 需要用户明确授权推送权限
- 本地通知在 App 被 Force Quit 后不触发（iOS 14+ 行为）
- 解决方案：依赖 Background App Refresh + App 启动时补偿逻辑

### 8.3 后台任务执行限制
- iOS 限制后台任务执行频率（Background App Refresh 约 1-2 次/天）
- 解决方案：自动延期逻辑在 App 启动时执行一次补偿扫描，不依赖纯后台触发
- 关键通知（如任务开始提醒）依赖本地通知，即使 App 在后台也能触发

### 8.4 吐槽系统风险
- 吐槽文案如果过于冒犯，可能引起用户反感而非动力
- 缓解措施：
  - 默认"正常模式"，确保吐槽有趣但不伤人
  - 首次使用时说明产品调性，让用户有心理准备
  - 允许用户反馈"这条吐槽不喜欢"来优化文案库

### 8.5 外部依赖
| 依赖 | 版本 | 用途 |
|------|------|------|
| expo-notifications | 最新 | 推送通知 |
| expo-sqlite / watermelonDB | 最新 | 本地数据存储 |
| expo-background-fetch | 最新 | 后台任务触发 |
| expo-task-manager | 最新 | 任务调度 |
| react-native-reanimated | 最新 | 动画支持 |

## 附录：术语表

| 术语 | 定义 |
|------|------|
| 项目（Project） | 一个正在进行的工作主题，包含多个子任务 |
| 子任务（Subtask） | 项目下可重复执行的工作单元，定义时间段和重复规则 |
| 任务实例（TaskInstance） | 子任务在特定日期生成的具体任务 |
| 打卡（Check-in） | 用户标记任务开始和完成的行为 |
| 延期（Rollover） | 未完成的任务自动滚入次日 |
| 补卡（Make-up） | 对过期任务手动标记完成 |
| 跳过（Skip） | 用户主动放弃某个任务，不参与统计 |
| 连续打卡天数（Streak） | 连续有完成记录的天数 |
| 吐槽（Roast） | 根据延期次数分级的督促文案 |
| 周结算（Weekly Review） | 每周日生成的完成报告 + 评语 |
| 骂人烈度（Roast Level） | 用户自定义的吐槽强度：正常/火力全开 |
